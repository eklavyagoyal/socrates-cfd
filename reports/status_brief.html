Research prototype · status brief

Can an AI-assisted system tell when a CFD simulation is wrong?

socrates-cfd · OpenFOAM v2412 · benchmark: 2D flow past a cylinder at Re = 100 · 19 October 2026 · results are partial; the benchmark is still running

Simulation software can finish without a single error and still give the wrong number, because of a mesh that is too coarse, a domain that is too small, or a typo in the set-up. Today an expert catches this by running extra simulations by hand. This prototype automates that: it runs a simulation, gathers the evidence, decides whether the answer can be trusted to the requested accuracy, and runs targeted extra simulations when it cannot yet tell. An LLM may choose the next experiment, but it can never decide the verdict.

How it works

1 · SimulateOpenFOAM runs the case, generated from a structured problem spec
→
2 · EvidenceLogs, mesh quality, force histories and statistics, extracted deterministically
→
3 · ChecksRules with cited thresholds → PASS / FAIL / INCONCLUSIVE, plus an error budget
→
4 · CriticLLM (or a fixed rule list) picks one of 4 allowed experiments
→
5 · VerdictACCEPT / REJECT / INCONCLUSIVE, always from the deterministic checks

The four experiments are: refine the mesh, shrink the time step, enlarge the domain, run longer. Each result shows how far the answer moves, and that gives an uncertainty estimate (Richardson / Celik GCI). The loop repeats until the verdict is decisive or the budget runs out (≤ 6 experiments, ≤ 12× the original compute).

Authority limits on the LLM.
  • It sees only recorded evidence, with run names anonymised so they cannot leak which flaw a case has.
  • It can only return a request for one validated experiment, and it has no shell access.
  • A proposed ACCEPT or REJECT is refused and fed back as an authority violation.
  • Every number it writes is audited against the evidence; untraceable numbers are counted.

The benchmark

The question: the time-mean drag coefficient and the shedding frequency (Strouhal number) of a 10 mm rod in a slow air stream, each to ±3 %. The benchmark has one careful baseline, two careful variants, two borderline variants, and twelve plausible-but-wrong set-ups: a coarse mesh, a domain that is too small, a large time step, a steady solver, the wrong viscosity, the wrong force reference, premature averaging, and others. Each case is scored against the in-house converged reference (page 3).

What the adaptive loop adds

On B1 the static verifier cannot decide, and its checks all pass. The LLM critic read the evidence and asked for one experiment, enlarging the domain. Drag moved by 8.9 % and St by 6.7 %, both more than the 3 % tolerance, so the case was rejected. The fixed rule list reached the same verdict, but only after refining the mesh twice and halving the time step first.

This is the pre-registered "primary demonstration": OpenFOAM sees nothing wrong, the static verifier is inconclusive, and one targeted experiment exposes the flaw quantitatively.

Extra compute, relative to the original run

Both systems reached the same verdict on each case: REJECT on B1, INCONCLUSIVE on the baseline. The LLM was 8× cheaper on B1 but more expensive on the baseline (cost $0.60 in LLM calls), so whether the LLM adds value overall is not settled until the benchmark finishes.

The baseline and the reference answer

Scoring every case needs a "true" answer, and published values are only good to about 1 % because they come from finite domains and different codes. So the project built its own converged reference. It runs the baseline at finer meshes, smaller time steps and larger domains, and extrapolates each effect to zero (Richardson extrapolation).

Baseline lift (top) and drag (bottom) over 150 flow-through times. Shedding settles after about 70; the shaded window is the declared averaging window.

Getting a ±1 % reference took four stages and 13 extra simulations. Independent fact-checks of the draft reports pushed each step.

A design flaw the project found in its own tool. The "enlarge the domain" experiment keeps the growth rate of the cells, so the outer mesh gets coarser as the domain grows (the last cell grows from 1 to 4 diameters). Refining the outer mesh of the largest domain raised drag by 0.16 %. This skews every domain study the system runs. It makes the verifier more cautious (it overstates the domain effect), which is safe, but it cannot be accepted as a design. A domain experiment at constant outer resolution is the first thing to rebuild.
A false rejection explained. Every system rejects case J1, whose answers are within 1.1 % of the reference. The rejection comes from an extended mesh-quality check that fails on 48 stretched cells beside the outlet, 47 diameters behind the cylinder. That is a heuristic firing far from where the forces are produced.

What we have learned so far

1
Ordinary solver diagnostics are not verification. OpenFOAM's own checks accepted 6 of the 7 clearly broken cases. The benchmark's flaws are not trivial for existing tools.
2
Deterministic checks are safe but often silent on one run. They have not accepted a single bad answer, but without extra simulations they decide only the set-up errors (steady solver, wrong viscosity, wrong reference).
3
Targeted experiments expose numerical flaws. One mesh refinement exposed A1, and one domain enlargement exposed B1, each at roughly the cost of the original run.
4
Rigour is expensive and conservative. Even the careful baseline cannot be formally ACCEPTed: its real drag error (about 1.2 %) is too close to the per-component limit (1.5 %) to be proven below it, after 5–6 extra simulations costing 7–8× the original run.
5
An LLM reading the evidence alone is a strong baseline. With no experiments and no checks it flagged all 7 broken cases from configuration "smells" such as a coarse mesh or an upwind scheme. But its ACCEPTs rest on no demonstrated accuracy. The attack cases, built to look clean, test whether it can be fooled.
6
"Plausible but wrong" is often not wrong at 3 %. Five of the twelve deliberately flawed set-ups (C1, E1, G1, G2, J1) land within 2 % of the reference. A useful verifier must quantify how wrong an answer is, not just spot bad practice.

Still open

  • Finish the benchmark. C-rule has decided 7 of 17 cases, C-llm 6 of 17 and the exhaustive protocol 2 of 17. The three attack cases have barely started (the inlet-shear attack is caught only by an extended check, and only as a set-up problem).
  • The pre-registered value tests.
    • Does the adaptive system resolve cases the static verifier leaves open? So far yes: A1 and B1.
    • Does the LLM beat the fixed rule list on accuracy or cost? Mixed so far: cheaper on B1, dearer on the baseline.
    If the LLM adds no measurable value, the final report will say so.
  • Ablations. Repeated LLM runs (how consistent are its choices?), an acceptance-review gate, and verifier extensions against the attacks.
  • Final report. Answers to the 13 research questions: what it detects, what remains, false-acceptance rate, compute overhead, product potential, and what to build next and what not to build.
Caveats.
  • One benchmark (laminar 2D cylinder) and 17 cases: rates are indicative, not statistically strong.
  • Several labels sit near the tolerance boundary, so two label views are reported: the pre-registered rule, and the rule with the reference uncertainty taken into account.
  • All numbers here are interim and will be updated when the runs complete.
